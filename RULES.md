# FitTrackr Production Engineering Rules & Architectural Invariants

**Document Version:** 1.0.0-STRICT  
**Enforcement Level:** MANDATORY (Zero Exceptions)  
**Applicability:** All Dart/Flutter code, Kotlin Native Bridges, Gradle Configurations, and UI Components  

---

## 1. The Zero-Fake-Data Invariant (Rule 101)

### 1.1 Prohibition of Synthetic & Mocked Telemetry
Under NO circumstances shall any component in the production code path generate, simulate, or display fake, randomized, or hardcoded telemetry:
* **PROHIBITED:** `Random().nextInt(10000)` or `Timer.periodic` generating fake step increments.
* **PROHIBITED:** Mock repositories returning static lists of completed workouts unless explicitly located in `test/` directory mock fixtures.
* **PROHIBITED:** Hardcoded strings for calorie burn, distance, or active minutes (e.g. `Text("8,432 Steps")`).
* **REQUIRED:** Every single step count, active calorie value, distance meter, and heart rate point MUST originate from:
  1. The **Android Health Connect API** (`androidx.health.connect.client.HealthConnectClient`), OR
  2. The onboard **Android Hardware Step Counter Sensor** (`android.hardware.Sensor.TYPE_STEP_COUNTER`), OR
  3. The local, persistent **Drift / SQLite Database** containing historical records previously written by the above APIs or explicit user log entries.

### 1.2 Graceful Absence vs. Falsification
When telemetry data is unavailable (e.g. fresh install, permissions not yet granted, or hardware sensor missing):
* The app MUST render an **Explicit Ground-Truth State** (e.g., `0 Steps`, `No activity recorded today`, or an actionable `[ Connect Health Connect ]` permission button).
* The app MUST NEVER inject "sample" data to make the screen look populated.

## 2. Anti-AI Slop & Content Integrity Policy (Rule 102)

### 2.1 Complete Ban on Gimmick Chips and Hallucinated Terminology
The user interface and codebase shall remain strictly free of "AI slop", pseudoscientific buzzwords, and marketing placeholders:
* **STRICTLY FORBIDDEN UI LABELS & CHIPS:**
  * ❌ `"AI Smart Burn"`, `"Neuro-Workout Optimizer"`, `"Quantum Calorie Sync"`
  * ❌ `"Magic Detox Suggestion"`, `"Synergistic Wellness Score"`
  * ❌ `"Smart Plan Generated by FitAI"`
* **STRICTLY ENFORCED ATHLETIC TERMINOLOGY:**
  * All exercise and workout concepts MUST adhere to standard sports science and kinesiology:
    * `Volume Load (kg)` = $\sum (\text{Weight} \times \text{Reps})$
    * `RPE` = Rate of Perceived Exertion (Borg CR10 Scale, 1 to 10)
    * `1RM` = One-Repetition Maximum (Calculated via Brzycki or Epley formula)
    * `BMR` = Basal Metabolic Rate (Calculated via Mifflin-St Jeor formula)
    * `TDEE` = Total Daily Energy Expenditure (BMR $\times$ Activity Multiplier)
    * `Cadence` = Steps per minute (Calculated via timestamped step deltas)

### 2.2 Verified Nutrition Only
* No auto-generated recipes or imaginary food items.
* Food queries MUST hit real, verified REST endpoints:
  * **Open Food Facts API:** `https://world.openfoodfacts.org/api/v2/product/{barcode}`
  * **USDA FoodData Central API:** `https://api.nal.usda.gov/fdc/v1/foods/search`
* If offline, search queries only surface foods previously logged and cached in the local SQLite `foods` table.

## 3. Real Android Health & Native API Rules (Rule 103)

### 3.1 Health Connect Protocol (Android 14+ Built-in / Android 9-13 App)
1. **SDK Dependency:** Must use official AndroidX Health Connect:
   `androidx.health.connect:connect-client:1.1.0-alpha11` (or latest stable release).
2. **Availability Check:**
   Before initiating any query, check `HealthConnectClient.getSdkStatus(context)`. Handle all three states:
   * `SDK_AVAILABLE`: Proceed with permission request and telemetry read.
   * `SDK_UNAVAILABLE_PROVIDER_UPDATE_REQUIRED`: Redirect user to Google Play Store to update/install Health Connect APK.
   * `SDK_UNAVAILABLE`: Fallback seamlessly to Tier 3 hardware step sensor (`Sensor.TYPE_STEP_COUNTER`).
3. **Samsung Health Interoperability:**
   * Samsung Health on Galaxy devices automatically synchronizes steps, workouts, and heart rate into Health Connect.
   * FitTrackr must NOT attempt to reverse-engineer proprietary Samsung SDKs; it utilizes the official Health Connect bridge which Samsung Health officially supports on Android 10+.

### 3.2 Hardware Step Counter Fallback Rules
1. **Sensor Identifier:** Must use `Sensor.TYPE_STEP_COUNTER` (cumulative steps since boot), NOT `Sensor.TYPE_STEP_DETECTOR` (which wakes up CPU on every single step and causes severe battery drain).
2. **Boot Reset Handling:**
   Because `TYPE_STEP_COUNTER` resets to `0` whenever the user restarts their phone:
   * The background service MUST store `last_raw_sensor_value` and `boot_timestamp` in persistent storage.
   * When `current_raw_value < last_raw_sensor_value`, a system reboot has occurred. The system must create a new baseline offset.
   * Daily step count calculation formula:
     $$\text{Steps Today} = \text{Sensor Now} - \text{Sensor At Midnight} + \sum \text{Reboot Deltas}$$
3. **Android 14+ Foreground Service Requirement:**
   * The background step listener must run in a Foreground Service declared with:
     `android:foregroundServiceType="health"`
   * Must include `android.permission.FOREGROUND_SERVICE_HEALTH` in `AndroidManifest.xml`.

## 4. Architectural & Code Quality Standards (Rule 104)

### 4.1 Strict Layered Clean Architecture
```
lib/
├── data/
│   ├── local/          # Drift database, tables, DAOs, type converters
│   ├── remote/         # HTTP clients for USDA / Open Food Facts
│   ├── native/         # Kotlin MethodChannels & EventChannels
│   └── repositories/   # Implementation of domain repository interfaces
├── domain/
│   ├── models/         # Pure, immutable Dart data classes
│   └── repositories/   # Abstract repository contracts
└── presentation/
    ├── common/         # Atomic UI widgets, theme tokens, typography
    └── features/       # Feature folders (dashboard, workout, steps, progress, diet)
        ├── providers/  # Riverpod AsyncNotifiers & controllers
        └── views/      # Stateless and Consumer widgets
```

### 4.2 State Management Rules (Riverpod 2.x)
* **Code Generation Only:** Use `@riverpod` annotations; no legacy manual `ChangeNotifierProvider` or `StateProvider`.
* **Async Value Purity:** All asynchronous states must map to `AsyncValue.when(data: ..., loading: ..., error: ...)`. No unhandled future states.
* **Separation of Presentation:** Views MUST NOT execute direct database or platform channel calls. Views only invoke methods on Notifiers.

### 4.3 Database Rules (Drift / SQLite)
* All schema changes MUST have a corresponding schema migration test.
* Foreign keys MUST be explicitly declared with appropriate `ON DELETE CASCADE` or `ON DELETE SET NULL` constraints.
* Heavy queries (e.g. 90-day step aggregations or volume load charts) MUST be indexed on `(date)` and `(workout_id, completed_at)` to guarantee $< 16\text{ ms}$ execution on low-end hardware.

## 5. UI/UX & Visual Standard Rules (Rule 105)

### 5.1 No UI Jank or Layout Shifts
* **Tabular Numbers:** Monospaced fonts (`JetBrains Mono` or `Roboto Mono`) MUST be applied to all incrementing numeric counters, timers, and step totals to eliminate horizontal jitter.
* **Aspect Ratios & Bounding Boxes:** Card and list item heights must be constrained to prevent visual pop-in when remote images or chart splines render.

### 5.2 Material 3 Theme Conformance
* Do not hardcode ad-hoc colors inside widgets. All colors must resolve from `Theme.of(context).colorScheme` or the semantic token constants in `AppColors`.
* High-contrast accessibility compliance (WCAG AAA) is mandatory for all text and interactive icons.
